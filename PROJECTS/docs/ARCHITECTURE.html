A sieve, not a spider.

Crawler turns raw purchase requisitions into a short, defensible list of vendor documents. Five stages, one crawl engine, and roughly a dozen gates whose only job is to throw things away. This is the map: what the parts are, how data moves between them, and where the guardrails sit.

Figures from the validated end-to-end run of 2026-07-14. Each column is the input to the next, so the strip reads as the actual reduction ratio: about one PDF per 550 requisition rows.

01 — Components

The system map

One orchestrator, five stage services, two operator surfaces, and a single crawl engine that every download path must route through. The engine is deliberately the only door: the pipeline, the Tkinter GUI, and pdf_discovery_pipeline.py all call the same object.

Communication protocols

All inter-component communication is in-process function calls — there is no message bus, no RPC, no inter-service HTTP. The pipeline is a single Python process that imports and calls each stage sequentially.

HTTP session configuration

The scraper's _make_session() factory produces a requests.Session with:

  • User-Agent: Chrome 120 on Windows 10 (deliberate impersonation to avoid bot blocks)
  • Retry: 3 attempts, backoff factor 1.0, on status 429/500/502/503/504
  • Allowed methods: HEAD and GET only
  • Adapters: HTTPAdapter mounted on both http:// and https://
  • Rate limiting: _DomainRateLimiter enforces 2.0s between requests to same domain, max 3 concurrent suppliers

What is NOT used

No Django, no FastAPI, no Celery, no Redis, no RabbitMQ, no Docker, no cloud services, no API keys, no OAuth. The system is intentionally a local-only single-machine batch pipeline with minimal dependencies.

03 — Stages

The five stages, in enforced order

The numbering is not cosmetic. Classify must run before scrape, because the Type column is what decides which keywords the crawler is allowed to look for. Run them out of order and the scraper refuses to start rather than crawling on an unfiltered keyword set.

Sorts every line item into Instrument, Software, or Non-Instrument. Matching is whole-word — bare substring matching once scored "lysis" inside "anaLYSIS", which is how eleven identical MULTICLAMP rows disagreed with each other.

Keyword lists live as frozensets in the classifier source, not in the .txt files — a learning-mode run would overwrite the text files. Post-audit sizes: Instrument 160, Software 157, Non-Instrument 478.

Fuzzy-matches line items against the master list and the text of the downloaded PDFs at threshold 60, in low-CPU mode by default, then exports a timestamped results workbook. The last validated run matched 6 items.

Post-crossref housekeeping

  1. Matched PDF collection — copies every matched PDF into C:/Data/Crawler/review/<timestamp>/ for manual inspection alongside the results spreadsheet.
  2. Review purge — deletes review folders older than 30 days.
  3. Unmatched PDF purge — deletes PDFs in output/ older than 30 days that were not in the current match set. The dedup DB retains their hashes so they will not be re-downloaded.
04 — Security

Trust boundaries and the gauntlet

Crawler's threat model is mostly about untrusted remote content, not multi-user access: it fetches arbitrary files from arbitrary vendor websites and writes them to a Windows filesystem. The controls concentrate on that boundary — where a hostile or merely sloppy remote server could send a path, a redirect, or a payload the process shouldn't act on.

The download gauntlet

Every candidate PDF passes these checks in sequence. Any one of them can drop the file, and several of them run before a single byte of body is read.

What leaves the machine

  • Nothing from the requisitions. Input, labeled, and output data stay on local disk. There is no telemetry, no API key, and no cloud upload path in the codebase.
  • Vendor domain names, in search queries of the form site:<domain> filetype:pdf sent to DuckDuckGo and Bing. That reveals which vendors are being researched — not what is being bought.
  • Ordinary HTTP requests to vendor sites, which reveal your IP and a Chrome-shaped User-Agent to those vendors.
05 — Findings

Gaps worth knowing about

These are observations from reading the current code, not speculation. None of them block the pipeline; three of them concern the dashboard, which is the weakest part of the security story.

The dashboard binds to every interface with no authentication

app.run(host="0.0.0.0", port=443) in ops/dashboard.py. Anyone who can reach the machine on the network can read / and /api/status. Bind to 127.0.0.1 if the operator is local, or put auth in front of it.

It silently falls back to plaintext on port 443

If openssl is missing, cert generation fails, the code prints a warning and calls app.run(host="0.0.0.0", port=443) with no ssl_context — serving HTTP on the HTTPS port. Clients expecting TLS get a confusing failure, and anyone who connects plainly gets served.

The certificate is self-signed with CN=localhost

Generated on first run for 365 days, -nodes so the key is unencrypted on disk at ops/key.pem. Fine for a single-operator box; it authenticates nothing.

Crossref's primary file glob never matches

run_crossref looks for *_labeled.xlsx, but classify writes *_classified_v3.xlsx. Every run therefore takes the fallback branch — "any .xlsx in the labeled dir, most recent by mtime". It works today, but it will happily pick up an unrelated spreadsheet dropped in that folder.

strict_content_validation is off

false in both the config and the constructor default. The %PDF magic-byte check still runs, so the practical exposure is small — but the content-type rejection is advisory rather than enforced.

The User-Agent impersonates Chrome 120

Deliberate, and common practice for crawlers that would otherwise be blocked. Worth naming explicitly: vendor logs will not show that an automated tool visited.
